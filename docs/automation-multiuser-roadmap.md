# 觅途 Mitu：定时投递、账号注册与多人服务实施路线

版本：v1.0  
日期：2026-11-05  
状态：后续功能方案；本文不代表已经实现定时任务、账号注册或公网服务。静默投递已实现并部署，实现、Computer Use 本地模拟验证与限制见 [静默运行记录](quiet-delivery-plan.md)。

## 1. 最新目标与实施边界

用户最新目标是：先实现静默投递并验证可行性，再让常规投递能够按计划运行，最终把项目作为非盈利服务提供给其他求职者，支持账号注册。

这一最终目标已超出此前“只发布产品展示与演示”的范围。原展示站方案仍可作为产品介绍阶段，真实执行服务需要本文件中的账号、调度和隔离能力，不能把演示站直接接入现有单用户接口。

建议把“彻底自动化”落实为：配置经过用户确认后，正常情况下按时启动、自动筛选、投递、留存JD和总结；遇到登录失效、平台验证、额度不足或沟通结果不明确时暂停，保留现场并提示用户处理。验证码或平台人工验证不能被当作可自动绕过的普通错误。

本轮不创建真实计划、不自动发送招聘消息、不开放注册、不部署外网入口，也不更换原有许可证。

## 2. 当前架构为什么还不能直接多人使用

根据当前源码与项目文档：

- `BossJobService` 用单个全局运行状态管理任务；`PlaywrightManager` 维护同一Boss浏览器、登录资料和串行执行线程。
- Boss配置、投递记录、JD库和模型配置使用当前单用户数据库；现有业务表没有统一的用户归属和授权链路。
- 现有定时机制用于登录监控、SSE心跳和JD后台分析，尚无持久的“定时投递计划”和“计划运行记录”。
- 部分旧接口没有统一登录鉴权；JD及笔试接口则限制本机来源。只增加一个注册页面不能使这些接口具备用户隔离能力。
- 有界面浏览器、Windows OCR和桌面伴随进程是执行环境的一部分；网页访问者注册平台账号，并不等于其自己的Boss登录态已存在。

因此应分离“用户与任务管理”及“真实浏览器执行”，保留现有可用业务逻辑作为执行端基础。

## 3. 推荐最终架构：云端管理，本地执行

### 云端平台

云端部署产品站、注册登录、计划管理、执行端绑定、任务派发和运行状态。云端数据库保存平台身份、计划、权限、配额及必要的结果摘要；初期建议采用有事务和并发控制的关系数据库，例如PostgreSQL。

云端只接收运行所需的最少信息。用户可选择是否同步JD、报告或简历；默认不上传Boss Cookie、浏览器资料目录、账号密码、桌面截图和个人文件。

### 每位用户的本地执行端

每位用户安装觅途执行端，在自己的电脑完成Boss登录。执行端通过向外发起的HTTPS连接领取已授权任务，不要求开放本机端口到公网。

浏览器、Cookie和本地Windows能力留在用户设备；执行端只接受结构化投递任务，不接受任意脚本、任意URL、系统命令或远程桌面控制。设备配对使用短时一次性配对码，显示绑定账号及授权范围，设备凭据可单独撤销。

这条路线可以继续复用现有Chrome登录、静默运行、JD留存和本机能力，也避免平台集中保管所有用户的招聘账号。它需要明确说明：定时执行时，电脑、执行端和网络必须可用；云端计划不能在电脑关机后替它完成本地操作。

### 若未来要求完全托管执行

可以另立云端Worker方案，但每个用户必须具有隔离的浏览器会话、资料目录、任务锁、存储和运行权限；不能共享当前全局Chrome或数据库配置。浏览器Context只解决部分会话隔离，不能替代进程、文件、资源和访问控制边界。

需验证有界面运行、登录接管、平台网络访问和重启恢复，并限制并发、CPU、内存和队列。Windows OCR/桌面功能仍可能需要本地执行端。只有在这些能力与资源成本验证后，才评估是否提供完全托管模式。

## 4. 第一项后续功能：本地定时投递

### 用户界面

新增“定时计划”入口，支持一次性和每周指定日期/时间，第一版避免向普通用户展示原始Cron表达式。

每个计划明确显示：

- 计划名称、是否启用、时区（默认 `Asia/Shanghai`）、本地执行设备。
- 搜索关键词、城市、职位类型和筛选条件。
- 固定招呼语或AI模式及备用文本、图片附件选项。
- 每次搜索上限、每次沟通上限、每日累计沟通预算。
- 下次执行时间、上次结果、允许开始的时间窗口、暂停及取消入口。

计划保存时生成配置快照和版本。启用前显示实际发送范围及消息内容，用户明确启用才允许无人值守执行。不会把当前手动任务或已有配置自动转换成启用的定时计划。

修改搜索条件、消息、附件或执行设备后生成新版本；旧的未执行实例取消，已执行实例保留原快照。涉及发送范围变化时重新展示并启用授权，不在后台静默扩大任务范围。

### 持久化与触发

建议新增计划、运行实例、沟通操作账本三类数据。即使第一版只在本机SQLite运行，也不只使用内存定时器。

计划保存用户时区与本地时间规则，具体运行实例保存计算后的UTC触发时间。界面同时显示用户本地时间；跨时区及夏令时使用明确规则，不以服务器时区代替用户设置。

调度器扫描到期计划后，在事务中创建唯一运行实例；唯一键至少包含计划ID、计划版本和预定触发时刻。手动点击、重复扫描或服务重启不能为同一触发时刻创建第二次投递。

默认不补发错过的任务：设备离线、服务停止或超过开始窗口时，将该次记为“已错过”。重启后仅恢复查询和调度状态，不集中追发过去的计划；用户可显式发起新的任务。

### 并发、配额与去重

同一Boss账号同一时刻只运行一个任务，手动任务和定时任务共用锁与预算。账号当前忙碌时可在有效窗口内排队，窗口过期则跳过，不能无限堆积。

每日预算按用户选定时区的自然日累计，跨手动任务、计划和设备统一计数；平台侧实际限制可能变化，不把“每天150次”写成永久保证。用户在平台之外手动沟通消耗的额度无法准确得知时，应允许预留额度或人工调整，并将平台返回的限制优先执行。

发起沟通前先预留预算和记录操作ID，确认后记结果。计数按沟通尝试而不是仅成功消息；失败是否返还需明确，第一版沿用当前保守规则，发起后的异常不自动返还。

岗位去重键应包含平台账号与岗位标识；不能让另一个用户的投递记录阻止本用户，也不能因换了计划就向同一岗位重复发送。

### 不明确结果和人工接管

运行状态建议为：待执行、等待设备、执行中、需要人工、部分完成、完成、失败、取消、已错过。

网络断开或进程退出时，若操作尚未开始，可按策略重新领取；若点击“立即沟通”或发送请求已发生但结果未确认，则记为“结果待核对”，先回查聊天/投递记录。无法确认时暂停该岗位，不盲目重试发送。不能承诺第三方招聘平台上严格的“恰好一次”。

登录失效或验证出现时暂停后续岗位；用户可在工作台查看浏览器，处理后从已记录阶段继续。取消计划会阻止未开始的实例；停止正在执行的任务沿用协作式取消，不提前释放锁。

## 5. 账号注册与会话

建议首版采用邮箱注册、验证邮箱、登录、退出、忘记密码、设备管理；手机号和短信不是首版必需项。邮件/短信供应商、发信域名和费用在实施前选定，不能先宣称这些流程已可用。

注册和重置令牌应短时、单次有效并保存哈希；对注册、登录、验证和重置实施限速，错误文案避免泄露账号是否存在。未完成邮箱验证的账号不派发真实投递任务。身份认证与恢复流程参照[OWASP认证指南](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

密码仅保存经审核的自适应哈希，建议Argon2id；不保存可解密密码或把密码写日志。参数需按部署资源测试并保留升级能力。[OWASP密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

浏览器使用服务端可撤销会话与 `Secure`、`HttpOnly`、合适的 `SameSite` Cookie，敏感写操作同时防CSRF；登录后更新会话标识，退出及密码重置可撤销现有会话。避免把长期登录凭据放在浏览器本地存储。[OWASP会话管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

平台账号、Boss账号、设备身份是三种身份。绑定某个执行端后，其授权也仅限该用户的任务，不允许它读其他账号的JD或接收管理命令。管理员账号单独保护，管理权限不默认包含浏览用户Cookie、简历和私人聊天的能力。

## 6. 多用户隔离与设备派发

所有用户私有资源都需要可信归属：用户配置、计划、运行记录、JD/报告、文件、预算、设备和AI设置。服务端从经过验证的会话确定用户，不信任请求正文中可任意填写的 `userId`。

查询、更新、导出、统计、SSE/进度订阅和异步队列都执行归属检查；仅给表增加一列用户ID不够。缓存键、文件路径、去重键和配额同样带用户范围，公共示例数据与用户私有数据分开。[OWASP多租户指南](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)。

任务派发采用有过期时间的领取租约和心跳；租约只授权给指定用户、设备和运行实例。重复结果上传应幂等，过期设备不能覆盖新实例状态。排队消息携带经过验证的身份范围，执行时再次检查账号、计划和设备是否仍有效。

用户可随时撤销单台设备、暂停所有计划、退出会话或删除账号。撤销立即阻止新领取；已运行任务在下一安全检查点停止，不能把撤销视为强行终止已提交的第三方请求。执行端暂时断网超过租约后不得继续发起新的沟通。

公共注册初期采用邀请或限量开放，逐步验证容量。即使不收费，也要限制每用户队列、浏览器并发、数据体积和AI调用预算，防止少量任务耗尽共享资源。

JD及简历默认私有。未来公共岗位经验或统计应通过明确的选择加入和去标识处理，不自动公开个人JD库。AI摘要若发给第三方模型，应说明数据去向、范围及预算；平台公共模型额度与用户自带密钥分别管理，日志不输出密钥。

## 8. 分阶段交付与验收

### 阶段一：静默运行基础

先完成专用页复用、受控窗口后台运行、可查看/恢复以及人工处理提示。通过离线岗位及computer-use焦点验证，保留原投递、JD、消息确认、数量上限和停止回归。该阶段是后续无人值守的执行基础。

### 阶段二：本地定时计划

实现持久计划、配置版本、运行实例、预算账本、状态和暂停/取消界面，暂不依赖公网账号。测试使用可注入时钟及模拟执行器，不向真实岗位发送消息。

验收必须覆盖：同一分钟重复触发、两个调度实例争抢、午夜跨日、时区/夏令时、电脑离线、重启错过计划、手动与定时冲突、日预算耗尽、结果未知、取消竞态，以及任务已提交后进程崩溃。默认恢复不能形成补发或重复发送。

### 阶段三：注册平台与执行端配对

上线HTTPS平台、邮箱验证、可撤销会话、设备配对和可信任务派发，先小范围受邀使用。旧单用户接口在完成统一鉴权前不公开；不简单移除现有本机限制。

验收至少使用两个独立测试账号：相互猜测任务/JD/报告ID、导出、进度订阅、缓存复用、设备领取和密码重置均不能越权；撤销后任务不再发起沟通。邮件先使用测试发信环境验证，再接入选定供应商。

### 阶段四：公共非盈利服务

完成空库迁移、备份恢复、容量测试、数据保留/删除、依赖与许可证核对、错误监控、资源上限和运营入口，再逐步开放注册。部署使用可回退产物，回退不覆盖用户新增数据。

真实招聘消息的端到端验证，需要由具体测试用户明确选择账号、岗位范围、消息和发送额度；可以记录一份持续有效、可撤销的计划授权，无需对每次已授权计划重复确认。测试和平台运营不能代替用户作未授权的投递。

## 9. 实施前仍需决定

1. 先接受“云端管理 + 本地执行端”，还是要求平台承担完全托管浏览器；后者需要额外环境和容量验证。
2. 注册采用邮箱及所选发信供应商，是否先邀请制；当前未选定供应商。
3. 每位用户的默认预算、允许执行时间窗口、数据是否可选同步，以及用户可撤销授权的界面。
4. 原创部分拟用许可、上游授权边界和第三方依赖清单；本轮未完成全依赖法律审查。
5. GitHub账号/仓库、域名、托管区域及运营资源。不得在聊天中索要或记录明文密码、API令牌和Cookie。

上述决策可以在各阶段开始前明确；不会为了设计方案先开启任何真实定时发送、注册供应商或公网端口。
