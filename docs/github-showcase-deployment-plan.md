历史阶段范围：先上线产品展示与演示；该阶段不向访客开放真实 Boss 搜索、投递、账号登录或个人 JD 数据。用户随后将最终目标扩展为非盈利多人服务，新增定时投递与账号注册要求，最新路线见 [定时投递、账号注册与多人服务实施路线](automation-multiuser-roadmap.md)。本文件仍适用于独立展示站阶段。

## 1. 推荐方案

先将完整项目整理到自己的 GitHub 主仓库，再发布独立的静态展示站。主仓库建议先设为私有；展示站使用单独公开仓库，通过 GitHub Actions 构建并部署到 GitHub Pages。

推荐仓库名称示例：

- `<你的账号>/mitu`：完整产品源码、开发文档和版本记录，初期私有。
- `<你的账号>/mitu-showcase`：可公开的产品展示与模拟演示代码，公开。

如果你希望完整产品源码同时公开，可以在完成内容及历史扫描后公开主仓库；演示站与真实运行环境仍分离。仓库公开与网站可访问是两个独立选择。

GitHub Pages 适合托管 HTML/CSS/JavaScript 静态网站；它不能替代本项目的 Java 服务、SQLite 和浏览器执行环境。当前前端已经采用 Next.js 静态导出，展示站可沿用这一技术栈。[GitHub Pages 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[Next.js 静态导出说明](https://nextjs.org/docs/app/guides/static-exports)。

这条路线不需要先购买应用服务器，也不需要将当前电脑的 6866/9527 端口映射到公网。首版可先使用 GitHub 提供的域名；后续需要自己的品牌域名时再接入。

## 2. 对外展示什么

### 产品首页

沿用觅途蓝紫视觉和自有 Logo，介绍定位、核心能力和使用流程，提供“体验演示”“查看项目说明”“项目来源”入口。

重点展示：岗位筛选、投递任务管理、JD 自动留存、需求总结、简历准备依据。简历自动匹配及改写标为规划中，避免把尚未实现的功能写成已上线。

首页使用脱敏界面或重新生成的演示画面，不直接上传本机截图。截图需移除账号头像、个人介绍、真实招呼语、公司聊天、密钥和设备路径。

### 可交互演示

建议提供一条能完整体验的演示路径：

1. 选择“AI 应用开发 / 实习”等示例条件，查看模拟岗位列表。
2. 点击“演示任务”，观察模拟的检查、过滤和留存进度。
3. 打开 JD 岗位库，查看原文、版本和命中来源。
4. 进入需求总结，查看示例技能频次、证据引用和简历准备建议。
5. 重置演示，回到初始示例数据。

演示页始终标记“虚构数据 / 模拟流程”。统计数字由这批示例数据真实计算；示例 AI 结果标为预置演示，保留能对应示例 JD 的证据。

筛选、分页、详情、标签切换和版本切换可操作。真实沟通替换为流程预览；模型配置、Boss 登录、读取本机文件、截图、桌面进程和真实 AI 调用不接入演示站。演示无需访客提供简历、Cookie、账号或 API Key。

### 技术与来源说明

介绍当前实际架构：Next.js 前端、Spring Boot/Java、本地 SQLite、浏览器自动化、独立 JD 分析队列。明确展示站只有模拟数据，本地完整版才包含真实执行能力。

页面和仓库保留上游来源、许可证及必要声明；可以强调自己的品牌、界面和新增功能，但不宣称全部代码从零开发。

## 3. 展示站与真实系统的隔离

建议新增独立 `showcase/` 前端工程，单独构建。复用经整理的视觉组件、图标和展示逻辑，使用自己的页面外壳与示例数据接口；不直接将现有 `front/out` 整包公开。

原因是现有前端不只在业务按钮中调用 API：全局 `Sidebar` 会轮询健康状态，业务页还会读取配置、建立进度连接。只把“开始投递”按钮禁用，仍可能产生真实请求。

展示站应有独立的数据提供层，所有搜索、进度、JD、统计和报告都从内存或同站静态 JSON 获取。示例文件随代码受控，不能从当前 `getjobs.db` 自动导出。

独立发布链路为：展示源码 → GitHub Actions → 静态产物 → GitHub Pages → 访客浏览器。真实系统继续在本机运行，其数据库、浏览器资料和 Java 接口不参与该链路。

实施要求：

- 演示包不包含真实服务地址、Cookie、AI Key 或本机数据路径。
- 不挂载真实工作台的 API 轮询、SSE、WebSocket 和桌面功能。
- 演示数据加载失败时显示错误，不能回退连接 `localhost:9527` 或其他生产服务。
- 网络请求只加载演示站自身静态资源，不提交岗位或调用模型。
- 可增加仅允许同站连接的浏览器策略辅助防止误连；实际隔离仍以代码依赖和网络验收为准。

## 4. 当前项目在发布前需要处理的事项

以下为本轮源码和 Git 状态检查结果，不代表已经完成完整敏感信息审计。

### 4.1 Git 推送目标

当前 `origin` 仍指向 `https://github.com/loks666/get_jobs.git`。发布时应把该远程保留为 `upstream`，将自己的新仓库配置为 `origin`，并再次检查实际推送地址。

本方案不执行远程配置变更或推送。后续执行时，先整理发布分支及提交，再推送至明确指定的个人仓库；不重写现有工作区或覆盖上游仓库。

### 4.2 尚未入库的功能代码

当前工作区有大量已有修改，JD 功能的新增页面、服务和 `docs/` 等文件仍有未跟踪项。发布前应明确本次候选文件，确保当前运行功能的源码完整进入提交。

不直接把聊天工作区或整个父目录压缩上传。依赖目录、编译结果和运行资料不作为源代码提交。

### 4.3 敏感内容和历史

现有忽略规则已覆盖 `db/`、`browser-data/`、`cookies/`、`work/` 和部分环境文件。按受跟踪路径检查暂未发现这些运行数据，但仍需对候选提交、现有 Git 历史及图片做检查。

需要检查的内容包括：数据库及 WAL/SHM 文件、Cookie、登录资料、简历、AI Key、`.env.*`、原始岗位响应、运行日志、备份、系统截图和文档中的个人环境信息。公开展示仓库只复制经过审查的展示文件，不带主仓库历史。

`.gitignore` 不会移除历史提交中的数据；若发现凭据已经泄漏，应先撤销或轮换，再评估是否需要清理历史。[GitHub 敏感数据处理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。

### 4.4 许可证

仓库当前 `LICENSE` 为 **PolyForm Noncommercial License 1.0.0**，存在非商业用途限制。分发派生源码或复用的前端代码时，需要保留许可证条款/链接和上游 `Required Notice`；改名、改 UI 或设为私有仓库不改变其授权条件。[官方条款](https://polyformproject.org/licenses/noncommercial/1.0.0)。

本次按非商业产品展示规划。若展示页将用于销售、收费订阅、商业推广或其他商业用途，需先明确上游商业授权；不能因网站只做展示就自动认定所有商业场景都获许可。

### 4.5 可复现构建

当前 CI 仅有提交格式检查。`gradle.properties` 还固定了本机代理 `127.0.0.1:7897`，部分回归夹具位于忽略目录或仓库外。完整主项目后续要补可复现构建和受控测试，不能将本机“已通过”直接等同于 GitHub Runner 可构建。

展示站使用独立锁文件和构建流程，不依赖本机 Gradle 缓存、Java、Chrome 或 SQLite。完整应用的首次数据库初始化和驱动分发作为主项目发布的独立事项，不阻塞纯静态演示上线。

## 5. GitHub 与上线步骤

### 第一步：整理自己的主仓库

盘点源码和已有修改，备份本机运行数据；完成候选文件及历史扫描，保留来源与许可，整理 README、开发步骤和功能状态，再提交至自己的主仓库。

主仓库建议初期私有。需公开完整源码时，再检查内部协作记忆、旧截图和历史文件是否适合公开；对外 README 使用可复现相对路径及示例配置。

交付结果：自己的 GitHub 项目地址、清晰的来源说明、完整且无运行私有数据的代码提交。

### 第二步：制作独立展示工程

建立 `showcase/` 的首页和演示页；制作虚构岗位、JD 版本和报告，接入模拟进度与重置功能。蓝紫设计沿用当前品牌，产品说明区和工作台演示区分别布局，桌面与手机都能体验。

展示工程经过审查后独立提交到 `mitu-showcase`，保留涉及复用代码的许可和来源。首次维护可以使用受控文件清单同步，不必先配置跨仓库自动推送密钥。

交付结果：本地可预览、无后端依赖的展示站。

### 第三步：配置构建与 GitHub Pages

使用 GitHub Actions 执行固定版本的 Node/pnpm 安装、锁文件安装依赖、类型检查、演示逻辑检查及 Next.js 静态构建；只上传展示工程的 `out/`。

构建成功后通过 Pages 工作流发布。构建任务按最小权限读取源码，发布任务使用 Pages 所需权限及 `github-pages` 环境，禁止不可信 PR 触发正式发布。[GitHub Pages 工作流文档](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)。

部署只在指定分支和演示路径修改后触发，失败时保留上一版。依赖使用锁文件，Actions 依赖采用受控锁定方式或经过验证的提交 SHA。[GitHub Actions 安全使用说明](https://docs.github.com/en/actions/reference/security/secure-use)。

预期默认地址为 `https://<你的账号>.github.io/mitu-showcase/`。构建时需匹配仓库子路径配置，验证 CSS/JS、图标、内部链接及刷新后的直接访问；使用尾斜杠导出等适配方式，避免仅首页可访问。

### 第四步：验收并发布入口

完成以下验收，再把访问地址加入 GitHub README 和项目描述：

1. 首页、演示页、直接深链接、刷新和404表现正常。
2. 390/768/1280宽度下主体无横向溢出，键盘可操作。
3. 断开本机觅途服务后，演示仍可完整运行。
4. 所有模拟操作均无对本机端口、Boss、AI 服务或真实后端的请求。
5. 构建产物没有真实凭据、个人数据和运行数据库；示例明确标注。
6. 统计可由示例数据重算，AI 演示结论能对应示例原文。
7. GitHub 干净 Runner 可复现构建，代码更新后能重新发布；回退已验证的提交可恢复站点。
8. 来源和许可说明完整，规划功能与已实现功能明确区分。

交付结果：可外网访问的演示地址、发布记录及验收说明。

## 6. 时间、成本与需要的信息

首版工作量初估 **2–4 个工作日**：包括源码整理与检查、展示工程、模拟流程和发布验收；这是规划估算，历史敏感信息处理或授权确认可能增加时间。

本方案不需要应用服务器。先使用 GitHub Pages 的默认域名和适用账户额度；自定义域名费用、账户套餐和流量额度以实际选用服务为准。国内外目标网络都应做访问验证，不能承诺所有地区体验一致。

后续开始实施时需要明确：GitHub 账号/组织、主仓库是否公开、展示仓库名称，以及是否已有域名。没有域名也可以先发布演示，不要求在聊天中提供密码或令牌。

## 7. 后续若要开放真实功能

真实功能上云另立阶段处理，不直接把演示站切换到本机接口。现有应用具有这些明确差异：

- 前端 API 根地址目前指向 `localhost:9527`；线上需要同源路由，并调整空地址被当前回退逻辑覆盖的问题。
- 多数旧接口目前缺少统一身份认证，配置接口可读取系统配置；CORS不是登录或权限控制。
- JD 和笔试接口有本机来源限制，远程访问需要设计对应授权；不能简单删除保护。
- Boss 使用有界面的 Chrome 和持久化登录资料；桌面窗口/OCR依赖 Windows。本机登录状态也不能假定搬到服务器即可继续使用。
- 当前 SQLite 单实例运行，首次空库初始化、独立用户数据、浏览器会话隔离及部署备份均需设计。

个人远程使用可先评估经过身份认证的受控入口；多人真实使用还需要账号、任务、数据和浏览器隔离。Cloudflare 的官方方案也要求先设置访问策略并验证来源身份，而不是仅创建公开隧道。[Cloudflare 受控应用发布说明](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)。

本阶段只交付展示站时，这些真实后端改造可以保留为后续计划，避免影响当前本机可用功能。
